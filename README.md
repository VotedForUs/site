# @votedforus/site

AstroJS-based static website for congressional vote analysis. Provides a web interface to explore bills, votes, and legislators from U.S. Congress data.

## Features

- Browse bills by congressional term and bill type
- View detailed vote breakdowns with member voting records
- Sortable and filterable legislator vote tables
- Individual legislator profiles with voting history
- Senate and House analysis pages
- Server-side rendering with Astro

## Understanding recorded votes and which bills appear

This section is for casual viewers who want to know why only some bills show up on the site and what “passed” and “rejected” mean for a vote.

### Why aren’t all bills from Congress on the site?

The site only includes **bills that have at least one recorded vote**. If a bill has never had a vote that we count as “recorded” (see below), it won’t appear in the bill lists. In addition, bills whose most recent action is only something like “Referred to the House Committee…” or “Referred to the Committee…” are skipped, because they usually have no floor votes yet. So you’ll see bills that have had at least one floor vote we can show (roll-call, unanimous consent, or voice vote), and not every bill that exists in Congress.

### What is a “recorded vote”?

Here, a **recorded vote** means a vote where we can show the outcome (passed or rejected) and, when available, how members voted (or that it was by voice or unanimous consent). We treat three kinds of votes as recorded:

1. **Roll-call votes**  
   The House or Senate took an official roll-call vote (yeas and nays). We get these from Congress.gov and, where available, from House/Senate sources, and show the result and individual member votes.

2. **Senate unanimous consent**  
   The Senate passed the measure “without amendment by unanimous consent” (no roll call). We still count this as a recorded vote and show it as **passed**, with members marked as having voted by unanimous consent (UC).

3. **Voice votes**  
   The chamber passed or rejected the measure “by voice vote” (ayes vs. noes, no individual names). We count it as a recorded vote **only if** the action text does *not* say that someone “demanded the yeas and nays” or “demanded a recorded vote.” When a recorded vote is demanded, a roll call happens later, so we don’t treat the initial voice vote as the recorded vote. When we do count a voice vote, we show the outcome (passed or rejected) and mark members as having voted by voice vote (vv).

So: a bill is included on the site if it has at least one action that is one of these three (roll-call, Senate unanimous consent, or a voice vote we count).

### What does “passed” vs “rejected” mean for a vote?

For each recorded vote we show a single outcome:

- **Passed**  
  The measure was agreed to. We show “passed” when the official result text indicates passage, e.g. “Passed”, “Passed by Unanimous Consent”, “Agreed to”, or “Confirmed”.

- **Rejected**  
  The measure did not pass. We show “rejected” when the result is “Failed”, “Rejected”, or anything that doesn’t indicate passage. For voice votes we also look at the action description: if it says the “noes” prevailed or that the motion was “rejected,” we show “rejected”; otherwise we show “passed.”

So on the site, every recorded vote is shown as either **passed** or **rejected**.

### How does the site label bills (became law, in progress, rejected)?

Besides the result of each vote, the site assigns each bill a **state** from its latest action text:

- **Became law** — e.g. “Became Public Law” or “Signed by President.”
- **Rejected (or no longer in progress)** — e.g. “Failed of passage,” “Vetoed by President,” “Motion to proceed rejected,” “Cloture motion rejected,” or “Motion to discharge … rejected.”
- **In progress** — anything else (e.g. passed one chamber, awaiting the other, or in committee).

This helps you see at a glance whether the bill has finished its path or is still active.

## Prerequisites

- Node.js 24+ (see `.nvmrc` in monorepo root)
- npm 11+
- Data files generated from `@votedforus/votes` package

## Installation

```bash
# From monorepo root
npm install

# Or install the site package dependencies directly
cd packages/site
npm install
```

## Data Generation

Before running the site, generate the required data files using the `@votedforus/votes` CLI:

```bash
# From monorepo root - generate all data for the site
npm run site:legislators:generate       # Generate legislators.json
npm run site:bills:generate:all         # Generate all bill type files

# Or generate a demo dataset (5 bills per type)
npm run site:bills:generate:all:demo
```

### Data Files

The site expects these JSON files in `src/data/`:

| File | Description | Generated by |
|------|-------------|--------------|
| `legislators.json` | Current legislators (reduced format) | `site:legislators:generate` |
| `bills-hr.json` | House Resolutions with votes | `site:bills:generate:hr` |
| `bills-s.json` | Senate Bills with votes | `site:bills:generate:s` |
| `bills-hjres.json` | House Joint Resolutions | `site:bills:generate:hjres` |
| `bills-sjres.json` | Senate Joint Resolutions | `site:bills:generate:sjres` |
| `bills-hconres.json` | House Concurrent Resolutions | `site:bills:generate:hconres` |
| `bills-sconres.json` | Senate Concurrent Resolutions | `site:bills:generate:sconres` |
| `bills-hres.json` | House Simple Resolutions | `site:bills:generate:hres` |
| `bills-sres.json` | Senate Simple Resolutions | `site:bills:generate:sres` |

## Content Collections

The site uses Astro's content collections to load and validate data:

### Legislators Collection
```typescript
// From src/content.config.ts
const legislators = defineCollection({
  loader: file("src/data/legislators.json", {
    parser: (text) => {
      const data = JSON.parse(text);
      return data.map((legislator) => ({
        id: legislator.bioguide,
        ...legislator,
      }));
    },
  }),
  schema: legislatorSmallSchema,
});
```

### Bills Collections
Each bill type has its own collection:
- `billsHR`, `billsS`, `billsHJRES`, etc.

Access collections in Astro pages:
```astro
---
import { getCollection, getEntry } from 'astro:content';

// Get all HR bills
const hrBills = await getCollection('billsHR');

// Get a specific bill
const bill = await getEntry('billsHR', '119-HR-1');

// Get all legislators
const legislators = await getCollection('legislators');
---
```

## Configuration

### Astro Config (`astro.config.mjs`)

```javascript
export default defineConfig({
  outDir: '../../dist/site',  // Output to monorepo dist
  cacheDir: '../../.astro',   // Cache in monorepo root
  output: 'server',           // Server-side rendering
  adapter: node({
    mode: 'standalone'
  })
});
```

### Server Adapter

The site uses the `@astrojs/node` adapter for server-side rendering:

```bash
# Start the production server
node dist/site/server/entry.mjs
```

For static output, change the config:
```javascript
export default defineConfig({
  output: 'static',  // Static site generation
  // Remove adapter
});
```

## Utility Functions

### getBestBillTitle

Gets the most human-readable title for a bill:

```typescript
import { getBestBillTitle } from './content.config';

// Priority: Editorial title (from editorial/bills/{congress}/{type}/{number}.json) > Popular Title > Short Title (newest) > Original Title
const title = getBestBillTitle(bill);
```

## Development Notes

### Adding New Bill Types

1. Add the type to `BILL_TYPES` in `content.config.ts`
2. Create the corresponding data generation script
3. The collection is automatically created by `createBillCollection()`

### Zod Schemas

Schemas in `types.zod.ts` are auto-generated from `@votedforus/votes` types:

```bash
# From votes package
npm run build:schema
# Copies to site/src/types.zod.ts
```

### Type Safety

All data is validated against Zod schemas at build time, ensuring type safety across the application.
